# แผนตรวจรับและนำระบบแยกสลิปเดือนตุลาคม 2569 ขึ้นใช้งาน (ยังไม่อนุมัติ Deploy)

อัปเดตผลตรวจ: 15 ตุลาคม 2569 — เอกสารแผนปฏิบัติการเท่านั้น ไม่ได้สั่งเปลี่ยน Production

## เงื่อนไขที่ยืนยันแล้ว

- **PDF รูปแบบ A**: 1 หัวเอกสาร / 1 สลิปต่อหน้า
- **PDF รูปแบบ B**: 1–2 หัวเอกสาร / 1–2 สลิปต่อหน้า รวมถึงหน้าสุดท้ายของเดือนที่มีจำนวนบุคลากรเป็นเลขคี่
- ตรวจชื่อ–นามสกุลโดยตัดช่องว่าง + เลขบัญชี 10 หลัก + เลขตำแหน่ง 7 หลัก **ภายในสลิปเดียวกัน** กับ Google Sheets ก่อนบันทึก
- หน้าเว็บครูยังใช้เลขบัญชีค้นหาสลิปที่บันทึกแยกไว้แล้ว ไม่สแกน PDF ทุกครั้ง
- ไม่เพิ่ม OCR ไม่บังคับเทียบเดือนและปีที่พิมพ์ใน PDF
- การทดสอบและการเปลี่ยนโค้ดอยู่ใน Branch `fix/payroll-pdf-validation-no-deploy` เท่านั้นก่อนคำสั่ง Deploy ใหม่

## หลักฐานการตรวจรับที่ได้แล้ว

- ทดสอบฟังก์ชันและ Browser E2E ด้วยข้อมูลสมมติใน GitHub Actions ผ่าน (run 38705805537: 26/26 tests; Browser E2E สำเร็จ)
- ตรวจ PDF จริงเดือนมกราคม–ตุลาคม **เฉพาะในสภาพแวดล้อมภายใน** ด้วย PyMuPDF (ไม่ใช่ PDF.js): 10 ไฟล์, 338 หน้า, 376 สลิป, จับคู่ชื่อ–บัญชี–เลขตำแหน่งได้ 376/376, ไม่พบรายการซ้ำหรือไม่ตรง; ไม่ส่งเอกสารจริงเข้า GitHub
- ตรวจทะเบียน Google Sheets สด 39 แถวและเทียบข้อมูลกับสำเนาที่แนบ: ชื่อ บัญชี และเลขตำแหน่งตรงกันครบ 39 รายการ; บัญชี 10 หลักและเลขตำแหน่ง 7 หลักทุกคน

- Supabase Storage bucket `slips` มี 12 objects (นับจำนวนเท่านั้น); ไม่สามารถอนุมานได้ว่าเป็นไฟล์เดือนตุลาคมหรือไม่เมื่อ `upload_history` ของเดือนตุลาคมถูกลบแล้ว ห้ามลบ objects โดยคาดเดาจากจำนวน

## ประเด็นหยุดก่อน Deploy (Go/No-Go)

1. **ความลับข้อมูลเงินเดือน:** ตาราง `public.slips` และ `public.upload_history` ยังไม่ได้เปิด RLS และยังมีสิทธิ์ `anon` อ่าน/แก้ไข; bucket `slips` เป็น public — ต้องอนุมัติและตรวจรับแนวทางป้องกันการอ่านหรือแก้ไขข้อมูลข้ามบุคคลก่อนนำระบบใหม่ขึ้นจริง โดยคงรูปแบบหน้าเว็บเดิมตามความต้องการผู้ใช้
2. **การทดสอบ PDF.js กับไฟล์จริง:** การตรวจภายในด้วย PyMuPDF ผ่านแล้ว แต่ยังไม่ใช่การตรวจยืนยัน PDF.js ของเบราว์เซอร์จริงครบ 10 เดือน; ต้องทดสอบในสภาพแวดล้อมส่วนตัวที่ไม่ส่งข้อมูลจริงไปยัง GitHub หรือ log สาธารณะ
3. **สถานะสำรองข้อมูล:** ยืนยันว่ามี backup ที่นำกลับมาได้ของสลิปเดือนอื่นและข้อมูลที่จำเป็น ก่อนการเปลี่ยน Production; การไม่มีแถวตุลาคมในฐานข้อมูลไม่ได้ยืนยันว่ามีสำเนาของข้อมูลเก่าที่ถูกลบไป
4. **การบันทึกแบบสองขั้นตอน:** `slips` และ `upload_history` ยังบันทึกคนละคำสั่ง; หากการอัปโหลดค้าง `/api/admin/preflight` จะแจ้ง `stagedCount` และไม่อนุญาตให้อัปโหลดซ้ำ โค้ดไม่มีระบบล้าง staged rows อัตโนมัติ ต้องมีกระบวนการกู้คืน/ลบแบบปลอดภัยที่ตรวจรับก่อนใช้จริง
5. **การเข้าถึงด้วยเลขบัญชีเพียงอย่างเดียว:** การย้าย Supabase ไปหลัง API และเปิด RLS ป้องกันการดึงทั้งตารางได้ แต่ **ไม่ยืนยันว่าผู้กรอกเลขบัญชีเป็นเจ้าของบัญชี** ใครทราบเลขบัญชี 10 หลักก็อาจค้นหา/เปิดสลิปได้ ต้องให้เจ้าของระบบเลือกแนวทางยืนยันตัวตนและจำกัดคำขอก่อน Go/No-Go

6. **สิทธิ์ดำเนินการ:** การ Merge, Deploy, และการแก้ Production ยังไม่ได้รับอนุญาตแบบระบุรายการแยกจากงาน Branch ก่อนหน้า

## ลำดับปฏิบัติการหลังผ่าน Go/No-Go และได้รับอนุมัติ

1. ตรวจการสำรองและสิทธิ์การเข้าถึง Production โดยไม่รวมสลิปจริงลง GitHub
2. ทดสอบส่วนแยก PDF.js ด้วยไฟล์จริงแบบส่วนตัว; ตรวจผลว่าเดือนตุลาคมต้นฉบับ 19 หน้าแยกได้ 38 คน โดยทั้งหมดตรงกันครบสามรายการ
3. ตรวจรับมาตรการความปลอดภัยฐานข้อมูลและที่เก็บไฟล์ โดยไม่เปลี่ยนหน้าค้นหาสำหรับครู
4. เมื่อตรวจรับครบและได้รับอนุมัติชัดเจนจึงนำโค้ดที่ทดสอบแล้วขึ้น Production
5. ทดสอบหน้าเว็บครู/ผู้ดูแลบน Production โดยไม่เผยแพร่ PDF เงินเดือนจริงใน log หรือ screenshot สาธารณะ
6. ก่อนอัปโหลดเดือนตุลาคม ตรวจ `slips` และ `upload_history` สำหรับ (ตุลาคม, 2569) อีกครั้ง; **ถ้าเป็น 0 ทั้งสองตาราง ห้ามกดลบซ้ำ**
7. ผู้ดูแลอัปโหลด PDF ตุลาคมต้นฉบับ 19 หน้า ผ่านระบบใหม่; ต้องบันทึกได้ 38 สลิปที่ไม่ซ้ำ ไม่ปะปนข้อมูลบุคคลอื่น
8. ตรวจนับหลังบันทึก: `slips` เดือนตุลาคม 38 แถว / เลขบัญชีไม่ซ้ำ 38 / `upload_history` 1 แถว; ตรวจตัวอย่างการเปิดสลิปแต่ละส่วนโดยผู้ดูแลที่ได้รับอนุญาต
9. หากจำนวนไม่ครบ หรือพบสลิปผิดบุคคล ให้หยุดเผยแพร่เดือนตุลาคมและใช้แผนคืนสภาพภายใต้ผู้ดูแล — อย่าพยายามแก้ด้วยการเดาจับคู่หรืออัปโหลดซ้ำโดยไม่มีการตรวจระเบียน

## วิธีแยกสถานะอัปโหลดก่อนให้ผู้ดูแลดำเนินการ

- `clear=true`: ไม่มีทั้งสลิปและประวัติของเดือนที่เลือก จึงเริ่มอัปโหลดใหม่ได้
- `published=true`: เดือนนั้นเผยแพร่แล้ว ให้หยุด ห้ามอัปโหลดซ้ำหรือเขียนทับ
- `published=false` และ `stagedCount>0`: มีสลิปบางส่วน/ทั้งหมดอยู่ แต่ไม่มีประวัติเผยแพร่ ให้หยุด ตรวจนับและสอบสวนสาเหตุ ก่อนทำแผนล้าง/กู้คืนที่ได้รับอนุมัติ
- ห้ามสั่ง DELETE จากแถว staged โดยไม่ตรวจว่าเดือนนั้นไม่ได้เผยแพร่ในระหว่างคำขอ และไม่มี Admin อีกคนกำลังดำเนินการ ต้องใช้การควบคุมธุรกรรมหรือขั้นตอนปิดระบบเพื่อไม่ให้ชนกัน

## สิ่งที่ห้ามทำโดยอัตโนมัติ

- ห้ามลบหรือแก้ตาราง Production ระหว่างการเตรียมตรวจรับ
- ห้ามนำ PDF เงินเดือนจริง รายชื่อเต็มพร้อมบัญชี หรือข้อมูลเงินเดือนเข้าสู่ GitHub Actions, Git commits หรือ log
- ห้ามถือว่า CI ผ่านเท่ากับระบบข้อมูลเงินเดือนปลอดภัย เพราะ RLS และการเข้าถึงไฟล์ยังเป็นประเด็นแยก
- ห้ามถือว่าเลขบัญชีเป็นหลักฐานยืนยันเจ้าของที่ปลอดภัย; การจับคู่เอกสารถูกต้องไม่ใช่การยืนยันตัวตน

## ผลตัดสินใจที่ยังต้องขอผู้ใช้

- อนุมัติให้วางและทดสอบมาตรการคุ้มครองข้อมูล Supabase **โดยไม่เปลี่ยนรูปแบบหน้าค้นหาสลิปของครูหรือเข้าสู่ระบบ Admin** หรือไม่?
- เมื่อมาตรการดังกล่าวและการตรวจรับ PDF.js จริงผ่านแล้ว จึงขออนุมัติ Merge/Deploy แยกต่างหาก
