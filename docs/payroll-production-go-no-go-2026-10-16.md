**วันที่จัดทำ:** 16 ตุลาคม 2569  
**สถานะ:** DRAFT / NO-GO สำหรับ Production Cutover  
**Repository:** MrPhacharapon/slip-lpsec

**หลักการ:** เอกสารนี้เป็นแผน ไม่ใช่คำอนุมัติให้ Merge, Deploy หรือรัน SQL แก้ Production

## 1. ขอบเขตที่ต้องคงเดิม

- ครูค้นหาและเปิดเอกสารด้วยเลขบัญชีธนาคาร 10 หลักเท่านั้น ไม่เพิ่ม OTP, การเข้าสู่ระบบ, ชื่อ หรือเลขตำแหน่งในหน้าค้นหา
- Admin ใช้หน้าต่างรหัสผ่านเดิม ตรวจชื่อ–นามสกุล (ไม่สนใจช่องว่าง), เลขบัญชี 10 หลัก และเลขตำแหน่ง 7 หลักกับทะเบียน CSV ที่เลือกจากเครื่องหรือ API ทะเบียนที่ตรวจสิทธิ์ Admin ในขั้นตอนอัปโหลด; การเลือก CSV ไม่ส่งไฟล์ CSV ต้นฉบับเข้าเซิร์ฟเวอร์
- รองรับไฟล์รวมแบบ A (1 สลิป/หน้าทุกหน้า) และ B (2 สลิป/หน้า โดยหน้าเดียวที่มี 1 สลิปจะต้องเป็นหน้าสุดท้ายเท่านั้น); ไม่ใช้ OCR และตั้งแต่ข้อกำหนดที่ยืนยันเมื่อ 17 ตุลาคม 2569 ต้องตรวจเดือน–ปีที่พิมพ์ในแต่ละสลิปให้ตรงกับเดือน–ปีที่ Admin เลือกก่อน Stage (แก้ไขข้อความเดิมในร่าง 16 ตุลาคมให้ตรงพฤติกรรมล่าสุด)
- ห้ามนำ PDF เงินเดือนจริง เลขบัญชีจริง รหัสผ่าน Key หรือข้อมูลบุคลากรที่ระบุตัวบุคคลได้เข้า GitHub, CI, logs หรือแชท
- การรู้เลขบัญชีของผู้อื่นยังอาจทำให้เข้าถึงสลิปได้: ระบบค้นหาที่คงเดิม **ไม่ได้ยืนยันตัวตนเจ้าของบัญชี**; ต้องบันทึกเป็นความเสี่ยงคงเหลือก่อนเปิดใช้

## 4. จุดตรวจตัดสินใจ Go / No-Go (ทุกข้อบังคับ)

| Gate | หลักฐานที่ต้องมี | สถานะ ณ วันที่จัดทำ |
|---|---|---|
| G1: โค้ดทดสอบ | CI ของ Commit ที่จะ Deploy ต้องผ่านครบ, SHA ตรงกับที่ตรวจ | ดำเนินการระหว่างพัฒนา; ตรวจซ้ำเมื่อ Freeze SHA |
| G2: Real Test Integration | Next.js API → Supabase Test จริง, Stage/Publish/Search/PDF/Cleanup, ไม่ใช้ Production Secrets | **NO-GO: ยังไม่รัน** |
| G3: PDF จริง | PDF.js ทดสอบไฟล์ต้นฉบับทุกแบบ/ทุกเดือนในพื้นที่ปิด, จับคู่ 3 ข้อมูล และทวนผลครบ | **NO-GO: ยังไม่ตรวจรับครบด้วย PDF.js** |
| G4: Backup/Restore | Backup DB + Storage ต้นฉบับและ PDF สลิปที่ใช้งาน ตรวจ Hash/จำนวน และทดสอบคืนสภาพจากสำเนา | **NO-GO: ยังไม่ยืนยัน** |
| G5: Secrets / Domain | ตั้ง Environment server-only, รหัส Admin/Session/Rate Limit ใหม่, ตรวจ `APP_ORIGIN`, LINE, ไม่รั่ว client/log | **NO-GO: ยังไม่ได้ตรวจรับค่าจริง** |
| G6: Production Migration | ตรวจ duplicate/index, grants, RLS, Storage private/policies, RPC และแผนตรวจหลังเปลี่ยน | **NO-GO: ยังไม่อนุมัติแก้ Production** |
| G7: Legacy Storage | ตรวจบทบาท 12 objects รวม 3 รายการที่ไม่พบการอ้างอิงโดยไม่ลบทิ้ง; เก็บแผนใช้และคืนสภาพ | **NO-GO: ยังไม่ยืนยัน** |
| G8: อนุมัติ | ผู้ดูแลอนุมัติแผน Merge/Deploy และ SQL Production เป็นคำสั่งแยกอย่างชัดเจน | **NO-GO: ยังไม่มี** |

**กฎ:** ถ้าขาดหลักฐานแม้หนึ่ง Gate ให้คงสถานะ NO-GO ห้าม Deploy หรือปิดสิทธิ์ระบบเดิมกลางคัน

## 5. แผน Backup / Restore ที่ต้องตรวจรับก่อนขออนุมัติ

1. ระบุผู้มีอำนาจตรวจรับ, ช่วงเวลาบำรุงรักษา, ช่องทางแจ้งผู้ใช้ และขอบเขตสำรอง; ไม่บันทึกข้อมูลจริงลงเอกสารสาธารณะ
2. สำรองข้อมูล `slips` และ `upload_history` พร้อมข้อมูลคีย์/constraint/RPC/privileges และไฟล์ `slips` Storage ทุก object ที่เกี่ยวข้อง (รวมรายการที่ยังไม่จำแนก); แยกเก็บในพื้นที่ป้องกันสิทธิ์เข้าถึง
3. ตรวจนับจำนวนและ Hash/manifest ผ่านช่องทางส่วนตัว; ตรวจการอ่าน PDF จากสำเนาตัวอย่างตามสิทธิ์ที่เหมาะสม
4. **ทดสอบคืนสภาพในโครงการแยกหรือโคลนที่ได้รับอนุญาต** แล้วตรวจแถว/ไฟล์/สิทธิ์ตรงกับ manifest; ห้ามทดลอง Restore ทับ Production
5. เก็บสถานะและเวลา Backup/Restore, ผู้ตรวจรับ, ข้อผิดพลาด และแผนติดต่อ โดยไม่บันทึกรหัสหรือข้อมูลสลิปใน GitHub
6. สำรอง/ตรวจต้นทาง PDF เดือนตุลาคมก่อนอัปโหลด; ห้ามลบเดือนหรือไฟล์ต้นฉบับเพียงเพื่อให้ Preflight ผ่าน

## 6. ลำดับ Cutover ที่เสนอ (รออนุมัติ)

1. Freeze SHA และบันทึก CI/QA หลักฐานล่าสุด; ตรวจ Production aggregate และ duplicate/index ซ้ำทันที
2. ยืนยัน Backup ที่ Restore ได้จริง พร้อมวางช่วงหยุดการเขียน/ป้องกันการอัปโหลดระหว่างเปลี่ยนระบบ
3. ติดตั้ง SQL ที่ผ่านการตรวจรับอย่างเป็นชุด โดยตรวจ Unique Index, RPC, RLS, GRANT/REVOKE และ Storage policies/private bucket ตามแผนที่ได้อนุมัติ; ไม่รันสคริปต์ทดสอบทับ Production โดยตรง
4. กำหนด Secrets แบบ server-only และ Domain/Origin ให้ตรง; Deploy SHA ที่อนุมัติจาก Branch หลัง Merge ที่ตรวจรับแล้ว
5. ตรวจ API และหน้าเว็บแบบเฉพาะผู้มีสิทธิ์ ไม่แสดง PDF/บัญชีใน Public Logs; ตรวจ `anon` อ่าน/เขียนไม่ได้, Private Storage ดาวน์โหลดตรงไม่ได้ และ Service-role API ทำงาน
6. ตรวจรายงานเดือนที่มีอยู่ก่อนเสมอ; หากพบ Staged ค้างหรือประวัติแปลก ให้หยุดและตรวจด้วย Snapshot RPC; ห้ามลบอัตโนมัติ
7. อัปโหลดเดือนตุลาคมเฉพาะเมื่อ Preflight เป็น `clear` จริงและต้นฉบับผ่าน PDF.js + เทียบทะเบียนครบ; ตรวจจำนวนแยก, เลขบัญชีไม่ซ้ำ, มีประวัติ 1 แถว และสิทธิ์เปิด PDF ถูกต้อง
8. บันทึกผล Go/No-Go หลังการทดสอบจริง; หากไม่ครบให้หยุดเผยแพร่และเข้าสู่การคืนสภาพตามข้อ 7

## 7. แผน Incident / Rollback

- **จุดหยุดทันที:** API 5xx, สลิปผิดบุคคล, PDF เปิดไม่ได้, จำนวนไม่ตรง, เผยแพร่ผิดเดือน, สิทธิ์ public ยังเข้าถึงข้อมูลได้ หรือ Backup/Restore ไม่ผ่าน
- Freeze การเขียนและการเผยแพร่ใหม่; เก็บหลักฐาน non-sensitive ได้แก่ SHA, เวลา, status code, จำนวน/Hash เท่านั้น ห้าม log บัญชีหรือ PDF
- ตรวจว่าข้อมูลใดถูกเพิ่มในระหว่าง Cutover ก่อน Restore; **ห้ามทับหรือลบรายการใหม่ด้วยการคาดเดา**
- การย้อนกลับไปใช้ Deployment เดิมโดยเปิด RLS/Storage สาธารณะ **อาจกลับมาเปิดเผยข้อมูลเงินเดือน**; ห้ามอัตโนมัติคืนสิทธิ์ `anon` หรือเปลี่ยน bucket เป็น Public เพื่อให้เว็บไซต์เก่ากลับมาทำงาน
- หากถอยโค้ดกับ Schema อย่างปลอดภัยไม่ได้ ให้คงระบบหยุดการให้บริการส่วนที่เสี่ยงจนกว่าจะมีแผนแก้/คืนสภาพที่ผู้ดูแลอนุมัติ; รักษา Private Storage/สิทธิ์ข้อมูล
- Restore เฉพาะจาก Backup ที่ทดสอบแล้ว โดยผู้มีสิทธิ์และภายใต้แผน Change; ตรวจ Hash/จำนวน/RLS/Storage หลังคืนสภาพซ้ำ
- สรุปสาเหตุ ช่วงกระทบ และสิทธิ์เข้าถึงตามกระบวนการเหตุการณ์ข้อมูลส่วนบุคคลของหน่วยงาน

## 8. ผลสรุปปัจจุบัน

**NO-GO** จนกว่า Gate G1–G8 ผ่านครบและมีการอนุมัติแยก การผ่าน CI หรือ SQL aggregate-only เพียงอย่างเดียวไม่ใช่หลักฐานว่า Production ปลอดภัยหรือ Backup คืนสภาพได้

ไม่มีการแก้ไข Production จากขั้นตอนจัดทำเอกสารนี้
