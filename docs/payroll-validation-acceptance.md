# การตรวจรับระบบแยกสลิปเงินเดือน (Branch ทดสอบเท่านั้น)

## ขอบเขตที่ผู้ใช้ยืนยัน
1. รูปแบบ A: หนึ่งหัวเอกสารและหนึ่งสลิปต่อหน้า
2. รูปแบบ B: สองหัวเอกสารและสองสลิปต่อหน้า ยกเว้นหน้าสุดท้ายที่เหลือหนึ่งสลิปและหนึ่งหัวเอกสารได้เมื่อจำนวนบุคลากรเป็นเลขคี่; ห้ามมีหน้าเดี่ยวแทรกกลางรูปแบบ B
3. ตรวจ **ชื่อ–นามสกุล (ไม่สนใจช่องว่าง), เลขบัญชีธนาคาร 10 หลัก และเลขตำแหน่ง 7 หลัก** กับ Google Sheets ก่อนบันทึก

ระบุเลขตำแหน่งเป็น **ข้อความ** เพื่อเก็บเลข 0 นำหน้า ไม่ใช้ข้อมูลจากลำดับแถวแทนข้อมูลที่อ่านไม่ได้

## กระบวนการ
- ขณะอัปโหลด PDF: ผู้ดูแลเลือกไฟล์ CSV ทะเบียนจากเครื่อง (ไม่ส่งไฟล์ CSV ต้นฉบับขึ้นเซิร์ฟเวอร์) หรือใช้ API ทะเบียนที่ตรวจสิทธิ์ Admin และอ่าน Google Sheets ด้วยค่าฝั่งเซิร์ฟเวอร์ -> อ่าน PDF.js ตามตำแหน่งสลิปบน/ล่าง -> ตรวจเจ้าของทั้งสามข้อมูล -> ป้องกันบัญชีซ้ำ -> สร้าง PDF raster ใหม่สำหรับแต่ละคน -> บันทึกในตาราง slips
- หลังอัปโหลด: ผู้ใช้เดิมค้นหาสลิปที่แยกแล้วจากเลขบัญชีและเดือนบนหน้าเว็บตามปกติ ไม่สแกนเอกสารรวมใหม่
- หากสลิปใดระบุเจ้าของไม่ครบ/ไม่ตรงกัน หรือเดือนนั้นมีข้อมูลอยู่แล้ว: **ไม่บันทึกเป็นชุดใหม่**
- ไม่เพิ่ม OCR, ไม่เปลี่ยนระบบเข้าสู่หน้าเว็บ, ไม่บังคับให้เดือนและปีที่พิมพ์ใน PDF ตรงกับเดือนที่เลือก

## การทดสอบใน GitHub Actions
- ทดสอบฟังก์ชันจับคู่ด้วยข้อมูลสมมติ รวมชื่อผิด บัญชีผิด เลขตำแหน่งผิด และบัญชีซ้ำ
- ทดสอบ PDF.js กับ PDF จำลองที่มีข้อความภาษาไทยและตัวเลขแบบ Unicode
- เปิดหน้า Admin จริงด้วย Chromium แล้วจำลอง Google Sheets และ Supabase เฉพาะใน Browser Context
- ทดสอบ A หนึ่งสลิป, B สองสลิป, B สามสลิปในสองหน้า, ตรวจการค้นหาบนหน้าเว็บครู
- ตรวจ PDF แยกเป็นหน้าเดียวตามส่วนที่ถูกต้อง ไม่เก็บข้อความ PDF ดั้งเดิมไว้ในไฟล์ raster ที่สร้างใหม่
- ทดสอบการปฏิเสธทั้งชุดเมื่อพบชื่อหรือเลขตำแหน่งผิด และการปฏิเสธการเขียนทับเดือนเดิม

ไฟล์จำลองสร้างจากบุคลากรสมมติและเลขบัญชีสมมติเท่านั้น ไม่มีสลิปเงินเดือนจริงหรือข้อมูลส่วนบุคคลจริงใน Repository หรือ GitHub Actions

## สิ่งที่ต้องตรวจเพิ่มเติมก่อน Production
- การตรวจข้อมูลจาก PDF ต้นฉบับทั้ง 10 เดือนกับ PDF.js ในสภาพแวดล้อมที่รักษาความลับ (ไฟล์จริงไม่ส่งเข้า CI)
- Browser E2E ผ่านระบบ Supabase แยกจริงและทดสอบกรณีบันทึกไม่สำเร็จ ซึ่งยังไม่ได้ทำ
- สถานะใน Production เดือนตุลาคมต้องตรวจและซ่อมแยกต่างหาก (ไม่ดำเนินการโดยอัตโนมัติ)
- ฐานข้อมูลเดิมมีความเสี่ยงการเปิดอ่านโดย anon/RLS และ public storage ตามการตรวจครั้งก่อน; การแก้ไขเป็นคนละขอบเขตและต้องวางแผนไม่ให้ระบบเดิมหยุดทำงาน
- การ insert slips และ insert upload_history ปัจจุบันยังเป็นสองขั้นตอน **ไม่ใช่ transaction เดียวกัน**; หากการบันทึกประวัติล้มเหลวหลังบันทึกสลิปสำเร็จต้องติดต่อผู้ดูแล
- ผลปัจจุบัน: Full-project ESLint เป็นขั้นตอนบังคับใน GitHub Actions และไม่มี Errors; ยังอาจมีคำเตือนเกี่ยวกับรูปภาพ; TypeScript และ Build ผ่าน
