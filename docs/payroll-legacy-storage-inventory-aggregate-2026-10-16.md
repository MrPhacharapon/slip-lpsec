# ผลตรวจรายการ Storage เดิมสำหรับแผน Backup/Restore

วันที่ตรวจ: 16 ตุลาคม 2569 — **Production / อ่านอย่างเดียว** ไม่มีการเปิดไฟล์ แสดงชื่อไฟล์ ที่อยู่ Storage เนื้อหาสลิป หรือแก้ไขข้อมูล

## ขอบเขต

อ่าน Metadata ของ `storage.objects` ใน Bucket `slips` และตรวจเพียงว่ามีการอ้างอิงจาก `public.upload_history.storage_path` หรือไม่ ไม่มีการเปิด/ดาวน์โหลด PDF จริง

| กลุ่มไฟล์ | จำนวนไฟล์ | รวมไบต์ | ช่วงวันที่สร้าง |
|---|---:|---:|---|
| พบพาธในประวัติ | 9 | 48,982,540 | 20 ก.ค. – 10 ก.ย. 2569 |
| ไม่พบพาธในประวัติ | 3 | 14,759,310 | 19 ก.ค. 2569 |
| **รวม** | **12** | **63,741,850** | — |

Metadata มี MIME Type `application/pdf` ครบทั้ง 12 ไฟล์ และมีขนาดไฟล์ครบทุกไฟล์

## เงื่อนไขตรวจรับ

- ทั้ง **12 ไฟล์** ต้องถูกรวมใน Backup จริง ไม่ตัด 3 ไฟล์ที่ไม่มีประวัติอ้างอิงออก
- การไม่พบการอ้างอิง **ไม่ใช่หลักฐานว่าไฟล์ไม่จำเป็น**; ไม่อนุญาตให้ลบ ย้าย เปลี่ยนชื่อ หรือเปลี่ยนสิทธิ์ไฟล์โดยอัตโนมัติ
- บันทึก SHA-256 และขนาดของแต่ละไฟล์ใน Manifest ส่วนตัวที่จำกัดสิทธิ์เข้าถึง (ไม่เก็บ Manifest ที่ระบุชื่อไฟล์จริงบน GitHub)
- ตรวจว่าระบบใหม่ยังเปิดเอกสารย้อนหลังที่ถูกอ้างอิงได้หลัง Cutover ผ่าน API Admin ที่ตรวจสิทธิ์แล้วเท่านั้น
- ต้องทำ Restore ซ้อมในพื้นที่ส่วนตัวจาก **สำเนา Database + Storage จริง** แล้วตรวจจำนวน 12 ไฟล์และ Hash ของทุกไฟล์; ห้าม Restore ทับ Production

## ข้อจำกัด

ผลนี้เป็นการตรวจ Metadata อย่างเดียว ไม่ได้พิสูจน์ว่าไฟล์เปิดอ่านได้ ข้อมูลบัญชีถูกต้อง Backup จริงครบ หรือ Restore ใช้งานได้ Gate G4/G7 จึงยัง **NO-GO** จนกว่าจะมีหลักฐานจากการกู้คืนและตรวจเปิดไฟล์โดยผู้มีสิทธิ์

ไม่มีการแก้ไข Production ในการตรวจนี้
